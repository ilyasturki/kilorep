# Testing in a browser

A runbook, not a design document — it does not wind down the way the rest of
`docs/` does. It exists because driving the app through Chrome kept failing at
the sign-in screen for a reason nothing in the tree admitted to.

## The account

```
email     dev@kilorep.local
password  devdevdev
```

Public on purpose, and created by `scripts/seed.ts`, which refuses to run under
`NODE_ENV=production` because these credentials are in the repository. A real
instance gets its first account from `bun run account:create`, which never
touches the network.

**Never guess at these.** Read them here and type them once. Guessing is what
the next section is about.

If this password has drifted — a Settings change while testing, a half-finished
run — put it back rather than hunting for it:

```sh
printf '%s' devdevdev | bun run account:password dev@kilorep.local
```

That revokes every credential the account owns, which is the command's default
and the reason it is the recovery path: nothing here sends email, so a password
nobody remembers is answered at the machine. `--keep-tokens` opts out when the
change is a plain rotation. A Google-linked account has a second way, and it is
deliberately unadvertised in the UI: sign in with Google, then set a new
password from Settings, which asks for no old one.

## Why this used to fail

`/.data` is gitignored, so every worktree gets its own SQLite file — and a
fresh one has no accounts in it at all. The sign-in screen still renders, so
the failure looks like a wrong password rather than an empty database, and the
natural response is to try again.

`src/lib/server/auth/throttle.ts` is counting. Ten failures against one
address and account inside fifteen minutes, and login answers `429 too many
failed attempts`, locking you out of a server whose password you never had.
Fifty failures from the address across all accounts is the wider ceiling, and
nothing clears that one early.

Two things keep it from happening now:

- `.worktreeinclude` at the repo root copies `.data/kilorep.db` and its `-wal`
  into every worktree Claude Code creates, so the account is there before the
  server is.
- If it is not — a worktree made by hand, a database deleted, a torn copy —
  `bun run db:seed` creates it. The script is idempotent and prints
  `already seeded` on a second run.

## The content

The same script plants eight weeks of training on that account: five templates
— one of them a tombstone — and twenty-five finished sessions ending yesterday,
generated by `scripts/seed/content.ts` and shaped on a real log. It reaches the
browser the way any record does, through the launch sync, so sign in and it is
there.

Both halves are idempotent, and the content half knows its own rows by their
`seed-` prefix: `bun run db:seed --force` replants against today's date and
leaves anything you logged by hand alone. `delete from records where id like
'seed-%'` undoes it.

Deliberately more than a plausible log — the states are planted so every branch
of the UI has something to draw:

| State | Where |
| --- | --- |
| A plan never started | the Arms template, and four exercises with no history at all |
| A session with no plan left | the oldest workout — Upper Body is a tombstone, so History names it by its contents |
| Drift, all four kinds | the last Leg Day: a set added, the calf raises skipped, the leg curl retargeted, an unplanned cable crunch |
| A PR that is not the last session | Bench Press, two Push days back — "best" and "last time" read different numbers |
| An open rep target | Incline DB Press, where the rep field falls through to the hint |
| A set that counts nowhere | one unchecked pushdown, mid-block, beside the warmups |

`tests/seed-content.test.ts` is what holds those in place; a catalog slug
renamed out from under the seed fails there rather than in a screenshot.

Check before assuming, it costs nothing:

```sh
bun run account:list
```

If you are already throttled, restart the dev server. The counters are plain
maps in the server process with no persistence, so a restart is the whole
reset.

## Running it

```sh
bun run dev          # http://localhost:5173
```

The Chrome extension needs permission for `localhost:5173` before any of the
`mcp__claude-in-chrome__*` tools will touch the page — that is granted in the
extension, not from here, and it is a one-time thing per site.

Keep the tab you are driving **visible**. A backgrounded tab has
`requestAnimationFrame` frozen, so anything transition-driven — sheets,
overlays, the set-completion animation — is caught mid-flight and screenshots
as broken layout rather than as the bug you were looking for.

## Google sign-in

```sh
bun run dev:google   # http://localhost:5173, with .env.google loaded
```

`.env.google` at the repo root, read by that script and by nothing else — plain
`bun run dev` is untouched, and so are `bun run start` and drizzle-kit. It ships
with `ALLOW_REGISTRATION=1`; fill in the two Google lines. Missing, the script
refuses to start rather than serving a login screen with no Google button on it.

Nothing here can be diagnosed from the browser, which is why the file exists: an
unconfigured client and a closed instance both answer with a login screen that
draws no Google button, and that looks exactly like a correctly configured one you
are not allowed into. The endpoints under `/api/auth/google` are 404 for the same
reason — a self-hosted instance with no identity provider has nothing to say about
one. Half a client is the same as none; it resolves whole or not at all.

`ALLOW_REGISTRATION` belongs in this file and never in `.env`, which `bun run
start` also reads. It is needed because the first Google sign-in is a
*creation*: the seeded account is `dev@kilorep.local`, which is nobody's
Google address, so there is nothing for the identity to link to. Closed, the
callback redirects back to `/login` with a refusal rather than failing — the one
case here that does explain itself.

Then, in the Cloud console:

- the Authorized redirect URI must be `http://localhost:5173/api/auth/google/callback`
  exactly. A mismatch fails on Google's own page as `redirect_uri_mismatch`,
  before this server sees the request again.
- while publishing status is "Testing", only the addresses listed as test users
  can sign in. Your own is not there by default.

`http` on localhost needs no `ORIGIN`: `secureCookies` reads the request's scheme,
so the handshake cookie goes out without `Secure` and the browser keeps it.

After a successful run, `bun run account:list` shows the new account beside the
seeded one. `bun run account:delete you@gmail.com` puts you back to testing the
creation path from empty.

## The three states

**Signed in.** Sign in through the form at `/login`; that is the flow worth
exercising and the one place a real user's typing is reproduced. When the
session is only setup for something else, `POST /api/auth/login` with
`{"email":…,"password":…,"client":"web"}` sets the same HttpOnly cookie without
any typing to get wrong.

**Signed out.** `POST /api/auth/logout` revokes the credential the request
arrives with and clears the cookie. Then load any route under `(app)` and the
layout's guard should bounce you to
`/login?redirectTo=<the%20url%20you%20asked%20for>`, and signing in should land
you back on that URL rather than on Start. The reverse holds too: `/login` with
a good cookie redirects out, honouring `redirectTo` if it carries one.

Logging out is per credential by design — the browser signing out must not end
a workout on the phone. So a token issued to another device survives it, and
that is the correct result, not a leak.

**No server.** Not reachable in Chrome. `apiBase()` answers `location.origin`
on the web and `null` only in the app build, and it is `null` that the guards
read as local-only rather than signed-out. Testing that branch means the APK,
or a unit test against `setApiBase(null)`.

## The end-to-end suite

Everything above is for a person, or an agent, driving the app by hand. What a
release must never break is written down instead, in `e2e/*.spec.ts`, and run
by Playwright before every APK.

```sh
bun run test:e2e                                  # the whole suite, both projects
bun run test:e2e e2e/smoke.spec.ts                # one file
bun run test:e2e --project phone -g 'reaches History'   # one test, one project
```

On NixOS the browser Playwright downloads does not run. Point it at the
system's instead, every time:

```sh
export PLAYWRIGHT_CHROMIUM=/home/yasso/.local/state/nix/profile/bin/chromium
```

**What it drives is what ships.** `e2e/serve.ts` builds the server (`bun run
build:server`) and the app bundle, then starts `node build/server/index.js` on
a fresh database in a temp directory, migrated on boot and thrown away after
the run. The app bundle is built into `build/e2e-app` with `DEFAULT_SERVER`
pointed at that server — never into `build/app`, which `cap sync` would ship —
and served beside it. The server listens on `E2E_PORT` (default 4400), the app
bundle on the port after it; a session running beside another picks its own
pair. A server already on the port fails the run rather than being reused: a
stale build from another worktree is never what gets tested. The builds take
seconds, so there is no option to skip them.

Two projects run every spec: `phone` (420×860, touch, the coarse-pointer
styles) and `desk` (1280×800). A test that only exists on one carries a tag —
`test('…', { tag: '@phone' }, …)`, or `@desk` — and the other project skips
it. The browser speaks `en-US` whatever the machine does; a spec about French
formatting sets `test.use({ locale: 'fr-FR' })`.

**Accounts, one per test.** Tests run in parallel and write freely, so none
shares an account. Import `test` and `expect` from `e2e/fixtures.ts`, never
from `@playwright/test`, and ask for what the test needs:

| Fixture | What it is |
| --- | --- |
| `account` | A fresh, empty account, with `page` already signed in to it — on the web build and the app build both. `{ id, email, password }`. |
| `test.use({ seeded: true })` | Makes that account the seeded one: the eight weeks of *The content* above, planted for it in the run's database relative to now, and already pulled onto the device when the test starts. |
| `test.use({ google: true })` | Makes that account a Google-only one: no password, a Google identity instead. Signed in the same way. |
| `secondDevice` | A page in a second browser, signed in to the same account and holding nothing yet. Two of these make a sync test. |
| `token` | An API token for the account, for MCP and HTTP specs: `Authorization: Bearer <token>`. |
| `db` | The run's database, for the rare spec that has to look behind the API. |

None of them types a password. Accounts are written straight into the database
and signed in by session, so the throttle from *Why this used to fail* never
counts a thing. The smoke signs in through `/login` with the account's real
password. A spec about a refused password sends one wrong attempt against its
own account, and no more: every test in the run comes from the same address,
fifty failures from it lock out every sign-in for fifteen minutes, and
`--repeat-each=3` on two projects is six runs of that spec.

The app build lives at `APP_URL` (from `e2e/env.ts`): `test.use({ baseURL:
APP_URL })` and every `page.goto('/settings')` lands there. With `account` it is
signed in; without, it is a fresh install with no server named — the *No
server* state above, reachable at last.

**Helpers**, from `e2e/helpers.ts`, for the steps every area repeats:

- `startPlan(page, name)` and `startEmpty(page)` start a session from Train.
- `addExercise(page, name)` goes through the picker, in a session or a plan.
- `logSet(page, { kg, reps })` logs the set the session points at — typed into
  the tray on a phone, stepped on the desk ledger. Leave out what should stay
  as offered.
- `finish(page)` presses FINISH, answers the "sets still owed" question when it
  is asked, and resolves to the record's id. `openRecord(page, title)` opens the
  newest History row with that title.
- `readStore(page)` is the page's IndexedDB as plain data: `{ records, meta }`.
- `waitForSync(page)` waits until the server has acked every local write. It
  checks the store, so call it once the write is in there; called a moment too
  early it finds nothing dirty and returns. `syncNow(page)` starts a sync the
  way the network coming back does — the way to make a second device pull.
  Call it on a page that has drawn: offline while it is still loading, the
  page's own scripts fail and the app never starts, so nothing pulls.
- `plantRecords(db, account.id, page, rows)`, from `e2e/plant.ts`, writes
  templates and workouts straight into the account on the server — a session
  imported from v1, a plan archived or edited at a chosen time — then reloads
  `page` and waits until its launch sync has pulled them. It reloads rather
  than calling `syncNow`, which would kill a page that is still loading.
- `finishedSession(daysAgo, exercises)`, beside it, is one such workout: each
  exercise as `{ exerciseId, grip?, sets: [{ kg, reps, grip? }] }`, every set
  completed. It writes grips and slugs as given, so a session logged before
  a grip retired or an entry folded can be planted as it was stored.
- `bounds(locator)` is where a locator sits, `{ top, bottom, left, right }`,
  for the specs that are about layout. `themeColor(page, '--accent')` reads a
  theme colour back the way `getComputedStyle` reports one, to compare a
  control's colour against.
- `finger(page)` is one pointer whose every event carries its own timestamp:
  `down`, `move(to, ms)`, `up`. Playwright's mouse sends a drag's moves back to
  back, which anything measuring velocity reads as a flick, so a gesture whose
  speed matters (a swipe, the tray's handle, a sheet) goes through `finger`.
  `tap(at, roll)` presses, rolls and lifts in one burst, the quickest tap a
  thumb makes.

**Adding a spec.** One file per area, in `e2e/`, named for what it holds. Find
things the way a person does — role and name, `getByRole('button', { name:
'Log set' })` — and never by class. Wait on what the screen says, with
`expect`, and never with `waitForTimeout`: the suite runs with no retries, so a
sleep that is long enough on this machine is a red build on a slower one.

Before a spec lands it passes three times over on both projects:

```sh
bun run test:e2e e2e/<area>.spec.ts --repeat-each=3
```

A spec that fails one run in three is fixed, never retried and never skipped.

**When it fails**, the list reporter says which line; `playwright-report/` has
the HTML report and `test-results/` the trace of every failed test, with the
page at each step:

```sh
bunx playwright show-report
bunx playwright show-trace test-results/<test>/trace.zip
```

In CI the suite is a step of the `checks` job, after `build:app`. That job runs
on every push to main and every pull request, and the release workflow waits on
it — no APK is built from a red suite. The same two folders come back as the
`playwright-report` artifact when it fails.
