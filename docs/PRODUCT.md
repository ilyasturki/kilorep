# Product

## Domain model

- **Exercise:** name, equipment, load mode (`total` / `per-hand` / `unilateral`), body-weight share (see Math), muscle targets (one primary + secondaries, eleven coarse groups), search aliases, source (catalog or custom), optional rest-duration override, optional standing note — freeform text, the seat number and the grip, written and read on the exercise's own screen and never surfaced in the logging loop. A variation whose load or emphasis differs — incline, stance, a different machine — is its own exercise, linked to its canonical parent by `variantOf`: hints, history and PRs never cross entries, and lists fold a family into one row, variants behind an expander. A family has one parent, one level deep, and holds what a lifter would take for the same lift on another rack: every flat, incline and decline chest press under Bench Press, every overhead press under Overhead Press, every squat under Squat (the leg press roots its own), every fly under Dumbbell Fly; rows and curls keep a family per implement, where the implement is the lift's name. Every entry also carries a coarse movement `pattern` — horizontal or vertical press or pull, pullover, squat, lunge, hinge, fly, curl, extension, raise, shrug, abduction, adduction, carry, and flexion, brace or rotation for the core — which ranks what stands in for it: Swap's Similar shelf offers the family first, then the same pattern on the same primary muscle, then the muscle, so a machine chest press is offered presses before flyes. **Grip is the one variation that stays inside the entry**, as an optional single axis — a label ("Grip", "Attachment", "Handle"), a default, and its values, each of which may override the muscle targets. It splits nothing. A pull-up is one exercise whichever way the hands face, and so is every entry with an axis: hints and last time, history, raw PR, est-1RM and the calculator all read across grips, and the set keeps the grip it was logged with so the screens can say which it was. The hint names it where last time's differs from today's — `Last 8 reps · Supinated` — and the exercise's own screen opens on **All**, with a chip per value that narrows everything on it to one grip, the muscle badges included; opened from a workout, it opens on the grip in use there. All is a view and never a value: it reaches no set and no grip field. Sets per muscle is the one reading that still follows the grip, through its muscle targets, because a close-grip bench is a triceps set whichever history it sits in. A set logged before an axis existed reads as the default, with no migration to run. *Splitting was the first rule — history keyed on `exerciseId#grip`, each grip its own record — and it made one lift three: a pull-up done supinated left the next one, done pronated, saying First time, and the exercise screen counted each grip apart while the picker and Progress added them up.* Nothing was ever stored under that key, so dropping it rewrote no record. One axis, never two: the combinatorics of a second buy nothing a separate entry does not buy more honestly. An entry that became a grip on its parent (`close-grip-lat-pulldown`, `wide-grip-lat-pulldown`, `close-grip-bench-press`, `chin-up`) keeps its slug forever and is folded on the way out of the store — read, never rewritten, because last-write-wins sync would hand an older build a session naming an exercise it has never heard of. A grip value is never removed either: one taken off its axis is retired into a live value and read as it on the way out — the seated row's Straight Bar is its Wide Bar, the pulldown's Close is its Neutral — while a value put back (the seated row's Rope) is simply itself again. An axis that varies the hand says so in the lifter's words: Pronated, Supinated, Neutral. Same movement under another name is an alias, not a variant. The seeded catalog starts small and grows in the repo — entries append-only, a slug never deleted or reused, no descriptions, no photos, no video, ever; the one visual allowed is a bundled line-art illustration per entry and per non-default grip (`static/illustrations/<id>.svg` and `<id>--<grip>.svg`, every one drawn by the pipeline in `scripts/illustrations/PROMPTS.md`), so an underhand pull-up shows its own hands and never the overhand drawing; a grip without its own drawing shows the entry's, and an entry without one — every custom — is a state every consumer tolerates. Custom exercises are first-class alongside it (later; while the user base is one person, the rule is *grow the catalog, never a custom, for a real exercise*).
- **Template:** session → entries → exercises → sets. An entry holding several exercises is a superset. A planned set prescribes reps only, nullable = open target. Weight is never planned. The set count is stated in the same field the rep target is — typed or stepped, one to twelve, growing by repeating the last set's target and shrinking off the end; past a dozen is a typo, not a plan. A planned exercise may carry its own rest duration — absent, a number, or never-rest — stated and stepped on the exercise itself, inherited durations drawn faint and the plan's own in ink. A superset has one rest, per round, written on every leg so whichever leg closes a ragged round rests the same. A plan may also carry a default rest for every exercise it does not time itself; it lives beside the plan in a preference record of its own rather than in it, because a build that predates it rewrites a plan's top-level fields on save and would drop it. It may also be **optional** — the dips at the end, done on a good day: the session passes it by unless it is tapped, owes nothing for it, and the record says *Skipped, optional* rather than counting it as a set left behind. It is set from the exercise's menu in the plan and tagged *Optional* wherever the plan or the session shows it.
- **Workout:** a copy-on-start snapshot of the template tree, optional flags included, and a repeat copies them too. Editing a template never rewrites history; editing a workout never touches the template — except by the one door the record offers after the fact (Finish). Each exercise in it may carry a **session note** — a line about that day at that station, *seat moved to 5, left shoulder twinged* — written from the exercise's options (Add note) and drawn faintly under its heading, in the live list and the desk ledger while the session runs and on the record after. It is not the standing note: that one belongs to the exercise and stays on the exercise's own screen, where nothing in the loop reads it; this one belongs to the session. The next time the exercise is trained, the last note written for it shows under the heading the same way, marked as last time's, until a new one is written — read from the history it was written in and never copied into the new session, so a note goes out of date by being replaced rather than by being carried forward under a date it was not written on. Repeat this workout leaves it behind for the same reason: a repeat copies the structure, and the note was about the day. A swap leaves it with the lift it was written on, and it crosses only when the logged sets move across with it.
- **Set:** weight, reps, type (`normal` / `warmup` / `drop` / `failure`), RPE, completed, grip, arms. **Type** is a chip row in the set's sheet — Warmup, Drop, Failure — where none lit is an ordinary working set and tapping the lit one goes back to it. A warmup is lifted like any set: its row selects, its check logs, its swipe logs, and once logged it counts in nothing — no rest, no volume, no PR, no hint, no working-set number, so turning set 1 into a warmup makes set 2 the new set 1. Drop and failure are working sets in every reading; the type is recorded, and the row says so. *The sheet was once held open for a set note as well. The note went to the exercise instead, one per exercise per session: what a lifter writes down is about the station and the day, and a field on every set asked for it at a grain nobody writes at.* **Grip** is stamped when the set is made, from the exercise's own — never resolved late, or changing the exercise's grip mid-session would rewrite what an already-logged set says it was performed with; changing it moves the sets still to come and leaves the logged ones alone. **Arms** (`both` / `one`, absent = both) is recorded and nothing else: it splits no history, factors no volume and claims no PR. Forty kilos on a machine is forty kilos whether one arm pulls it or two — what changes is how hard it was and what it was for, which is a fact about that set worth keeping and nothing to compute from. The chip is offered only where a single side can actually take the implement — a dumbbell, a handle on a stack or a machine, a bell, a band — and never on a movement that is already one side at a time, or loaded by a bar or the lifter's own body: a one-arm pull-up is a feat, not a set option. *This replaces the per-set `single-side` (×1) load-mode override this section used to spec: the ×1 was wrong for a stack that does not change with the number of arms on it, and a mid-set drop to one arm is already its own `drop` set.* Type, grip and arms all live in the set's long-press sheet and put nothing on the logging card, which stays `weight | reps | check`; the exercise's own grip is chosen from the heading's options menu and reads back under the name, `Cable · Rope`. RPE is optional, never prompted, never prefilled and invisible to the check — one number stored on the 1–10 scale at half steps, which a preference relabels as RIR (`10 − rpe`); hint labels carry it where last time had one, `82.5 × 7 · RPE 8`.
- **Body weight:** date + kg, one per day, re-logging overwrites.

Math:

- **Load** = weight + bodyweightShare × the weigh-in in force on the day of the session. The number in the field is what was *added* — the belt, the vest, the dumbbell between the feet — because it is the only number a pull-up lets you change and the one the steppers are for; what the arms moved is that plus the body above them. Zero for everything loaded by a bar, a stack or a bell, so `load` and `weight` are the same number there and the field keeps saying `kg`. The weigh-in is read at the day of the session and never at the latest one: a lifter eight kilos lighter last spring did lighter pull-ups then, and reading today's number would redraw twelve weeks of tonnage every morning. It is computed rather than stamped into the set, so correcting a weigh-in corrects the sessions after it — and backdating one moves them, which is the same property read the other way. Before the first weigh-in ever logged there is no body weight, and a session there counts the added weight alone rather than an invented one.
- **Volume** = Σ load × reps × loadFactor (×2 for per-hand and unilateral), over completed working sets only.
- **Raw PR** = heaviest weight ever *added* on the exercise, tie-broken by reps at that weight. No formula. On everything loaded by a bar, a stack or a bell the added weight *is* the load, so this is the heaviest-ever it has always been; what it changes is the movement that carries a body. *Ranking the load was the first rule and it was wrong: a pull-up logs nothing on the belt, so load was the weigh-in and nothing else, the reps never entered the ranking at all, and the badge landed on the morning the scale read highest rather than the morning the lifter pulled best — one production history had it sitting on a session of four, four and five reps over a session of three sevens four days later. The claim it rested on — gaining weight at a constant belt is honest, since the lifter did pull more up — holds over a bulk and not over the kilo and a half between Tuesday and Friday, which is the only timescale the badge ever resolved at.* Ranking the belt gives that history its reps back, and the day something goes on the belt it leads again. The body is stated and never scored. The exercise screen calls it **Heaviest ever**, or **Most reps** where the belt has always been empty: *raw* carried the rule in a word only the code knew, and a tile sitting beside an estimate is the one that has to say it measured something. It states the load, names the added weight under it, or the body where nothing was added and a weigh-in says what the body weighed, and answers what went into the number — any grip or the one chip that is on, body weight included, no formula — on a tap of the label rather than in a line of prose nobody rereads. It is the one best, under that one name, everywhere a best is shown: the Exercises ledger's column, the swap picker's line, Progress's Strength card and MCP's `pr` read the same set, and the **PR** badge marks the set behind it.
- **Estimated 1RM** (Epley) reads the same load and is never the headline PR — a signal, and one the screens are careful to draw quieter than the best beside it. It says a direction on Progress's main lifts, and on the exercise's own screen, across grips or narrowed to the chip that is on: the current estimate, its twelve-week line, and a load calculator folded under a disclosure. The calculator is Epley read backwards — a weight and a rep count in, the estimate and the 1 / 3 / 5 / 8RM rungs out, seeded from the set the estimate came from, storing nothing and offering nothing to the logging card. It answers *what do I put on the bar today*, which is the question a trend raises and cannot answer. On a movement that carries body weight the rungs come back as what goes on the belt, the body subtracted on the way out, and a rung under an unloaded body says `body` rather than a negative kilo.
- **`bodyweightShare`** is a catalog field, coarse on purpose and stated on every `Bodyweight` entry including the zeroes: a pull-up (whatever the grip), dip and hanging leg raise carry all of it, a push-up about two thirds with the feet holding the rest, a back extension under half, and the core holds — plank, side plank, crunch, ab wheel, russian twist — carry none, holding a position being work no tonnage line has an honest way to count. Assistance is the same idea with the sign flipped and is deliberately not built: nothing subtracts, and the weight field stays at ≥ 0.

## The loop

**Start.** The app opens into Train, which is the way in: the session running, or the place one begins. The tab is two addresses and exactly one of them is true at a time: `/train/live` while a session runs, `/train` — one plan under the thumb and the rest in a list below it, an empty workout among them, everything else a door away — while none does, each redirecting to the other when the holder disagrees with it. The plan under the thumb is the one the rotation says is next: the plan after the last one you trained, in the order you dragged Templates into, wrapping at the end. The anchor is the last session that ran a plan rather than the last session, so an empty workout built on the gym floor is a detour and not a position; an untrained rotation reads from its own head. **The screen states the step it took rather than presenting the result as a fact from nowhere**: the caps header over the card carries it — *Next up · after Push A* — and says *first in your rotation* where there is no session behind it to have stepped off, which is the honest reading of a head nobody has trained into. A rotation of one says *again*, that being what a loop of one length does; *after itself* is true and reads as a bug. The line rides the header rather than the card because the card is already three lines of what the plan **is**, and a fourth about why it was picked competes with them for a width a phone does not have. This is arithmetic over your own history and nothing more — no model, no inference, nothing to configure, and reordering Templates is how you say it differently. With no plan at all there is no position to report and no card: the screen says there are no plans yet and offers the only two things true there — build one, or start empty — and drops its own All templates row, a door to a list of nothing being the second glance saying what the first one said. Nothing starts a workout except an explicit start: the editor's button or a tap on the idle screen, never navigation. On Plan's Templates half a row opens its editor, and Start lives inside it, under the thumb — immediate-start-on-tap was weighed and retired there: one row cannot honestly carry both "open this plan" and "begin lifting now", and a mis-tap that starts a workout costs more than the tap it saves. The idle Train screen is the one exemption: its rows can mean nothing but "begin", the screen itself is the proof no session exists to clobber, and a mis-tap starts an untouched session FINISH discards for free. "Repeat this workout" lives on any past workout in History and nowhere else: on the idle screen it was a second glance restating the first, since starting a plan and repeating the session that ran it are the same lifting, and the screen said Push A twice to say it. Exactly one workout is active at a time — starting a template over an unfinished session asks before it discards anything.

**During a set.** The screen shows what the next set needs: target or hint, weight, reps, check. The cursor steps past an optional exercise nobody has started to the next required one; a tap on any of its sets is how it is done, and from the first set logged or typed into, it is owed like the rest. Every set displays last time's actual weight × reps. The session list — exercise names, where you are — is the ledger itself on a desktop and one tap away on a phone, for orientation, jumping, reordering and inserting.

**Log a set.** The check commits exactly what's on screen — the hint if untouched, your edits if touched. The hint is never silently written: what the card offers is worked out where it is shown, from the carry, the target and last time, and a set reached and left again holds nothing — reading the offer is not entering it, and the offer cannot go stale because it is never stored. The first edit is what settles it: touching either number writes both, and from there the set holds its own, blanks included — a number cleared stays cleared, across a reload and out the other side. Clear set, in the set's own menu, is how the whole of one is taken back; on a logged set it asks first, for the same reason Remove does. Same-as-last-time is one tap. Deviating: ± steppers on the active set (±1 rep, and the weight in the jumps the implement actually has — ±2.5 kg off a bar or a stack, ±2 kg off a rack of bells, ±1 kg under ten where the dumbbells stop coming in pairs, the boundary belonging to the finer half so 10 − lands on 9 and 9 + lands on 10; stepping from the hint); tapping the number types into it. Bar: 1 tap when the value is right, ≤3 interactions when it isn't. **A warmup is offered a ramp** where a working set is offered last time: worked out from what the exercise's first working set offers — its own numbers, its carry or its hint, whichever it shows — the same way and under the same rule, computed where it is shown and never stored until the lifter edits or logs it. The rungs count up from the first warmup: ~50 % × 8, then ~70 % × 5, then ~85 % × 3, so one warmup is a half-weight set of eight and each one added in front of the working sets takes the next rung without moving the ones already there. With four or more the extra rungs go underneath, on the empty bar × 10 — 20 kg, on a barbell lift loaded past it — or ~30 % on anything without a bar. Every rung is rounded down to the implement's own jumps, so none reaches the working weight, and the card names the rung, `50 % of 100 kg`, where a working set names last time. On a movement that carries the body the percentages are of what was added, which leaves an unloaded pull-up warming up on the body alone and the reps doing the tapering. A working set with nothing to offer — never logged, nothing entered — leaves the warmups above it blank, as any set nobody can recall is.

**Rest.** The check starts one — mark done, start rest, advance. It is a clock in the top bar, on every tab and at every width so it survives the walk to Exercises mid-session, and never a screen of its own; the tray under the list keeps the next set's editor throughout, so logging a set shows the clock and the set that follows at once. Tapping the clock opens its controls: −30s, +30s and Skip move this rest only, and the default is never rewritten from the gym floor. Picking another set from the list is not declining the rest — only Skip or the next log ends one. A skipped rest is not gone: the clock becomes a Rest button that brings it back as if it had never been skipped, the same end, counting up if that end has passed, and the session snapshot keeps it so a reload does too. Working sets only: a warmup starts nothing, and a superset rests once per round rather than between its legs. Two minutes by default, a plan's own default where it has one, an exercise's own duration where it disagrees with either, and the plan's word on that one exercise over all of them — never-rest can be said at every level. A plan's durations, its default included, are copied into the session it starts, so editing the template mid-workout changes nothing under the lifter's feet, and a repeated workout rests the way that day did. At zero the phone is notified — a scheduled local notification, the only thing that reaches a dark screen — and the clock counts up until the next set is logged. Off for good in Settings; off for one session from the clock's controls, on a row of its own well clear of Skip, after which the bar says *Rest off* until a tap turns it back on. The app never holds the screen awake either way: the phone's own timeout is the user's setting and a 90-minute session is not the app's to override.

**Mid-workout.** Add and remove sets on any exercise; an exercise keeps its last one. Add warmup, in the exercise's options, puts a warmup in front of its working sets, after any already there, and takes the cursor only while nothing on that exercise is logged — once a working set is in, the rest it earned is the lifter's to keep. Reorder by drag from the session list; insert by catalog search, from the session list or from the foot of an exercise. An inserted exercise lands as its own entry right after the exercise it was inserted from, or at the end from the session list, with last time's set count (three when nothing recalls it). Add, swap and superset share one picker, on the gym floor, in a plan and in a past record alike: families fold under their parent with the variants behind an expander, what the session or plan already holds is marked, and the pick is the exercise — the grip comes with it only when the search named one, so *chin up* picks the pull-up held supinated and *pull up* picks the pull-up. Swap keeps the slot's plan — set count, targets, set types, rest — and the leg remembers the exercise the plan had there, which is what lets the drift count the slot as done. Once sets are logged on the outgoing exercise it asks what becomes of them, by name: moved to the new one with their numbers, kept on the old one while only the sets still to do move to the new one right behind it, or deleted. Set N recalls set N of the last session that reached it: when last time stopped short — fewer sets, or some left unchecked — the slot falls back to the most recent older session that had one, for the hint and the prefill alike. A set no session reached shows no hint and opens blank (check inert until values are entered); "First time" is said only of an exercise never logged, and a warmup recalls nothing: it is offered its ramp instead. No skip state: unchecked sets remain uncompleted. Back leaves the session without ending it — to wherever you came from, or to the Train home and its Resume card when nothing of ours is behind — and the session runs on with the tab's own dot as the way back in; FINISH is what *keeps* a workout, and Discard is what ends one without a record — the last row of the session list, set apart from the exercises above it (the drawer's foot on a phone, the ledger's on a desk), and the only destructive thing on the gym floor. It sits there rather than beside FINISH, because the panel is the one surface that speaks about the workout rather than the set in front of the lifter, and because two buttons under one thumb, one saving and one destroying, is the trade the template rows already refused. It asks before it does anything, and names what is lost by the count of it.

**Finish.** One tap, instant end, and what it settles into is the session's own record — the workout you just logged, sitting on top of History exactly as it sits when opened from the list, back walking up to the list rather than into an address that no longer holds anything. No summary, no ceremony: the record is the record and not a scoreboard, and the ceremony refused here was always confetti and share sheets, never the page the sets landed on. A session with nothing logged leaves no record to land on and rides its own redirect out to the idle screen instead — and the prompt says so, asking to discard rather than to finish, because one button doing two opposite things owes the lifter the name of the one it is about to do, and telling a session about to evaporate that it “ends as it stands” was the screen lying about the tap it was asking for. Unchecked sets stay in the record flagged uncompleted and are excluded from every stat; an untouched optional exercise's sets were never owed, so the finish prompt and the tray count them nowhere.

The gym floor is never asked about the plan. When a session went differently from the plan it ran, the record it lands on carries a quiet offer — *This workout differed from Push A: Bench Press +1 set · Dips added · Cable Fly not done* — with **Update Push A** and **Dismiss**, and the plan's own editor carries the same offer until one of them is tapped. Only the newest session of a plan offers, and the answer is a preference record per plan, never a key on the plan. A plan edited since the session began has answered already: Update would compare the session with a plan it never ran and undo the edit. Update copies structure and nothing else: exercises added and dropped, set counts, grips, order and supersets. Weights never; rep targets never, past a new set repeating the last one's. An exercise added and never lifted is not offered, and an optional exercise skipped or dropped is never proposed for removal — skipping it is what optional means. A swap fills the slot it replaced, so it is never offered as one exercise removed and another added: it reads *instead of Squat* on the record and is offered as its own switch, off until turned on — *Replace Squat with Hack Squat*. A workout with no plan behind it, or whose plan was deleted, offers **Save as a new plan** instead, on its record and in its ⋯ menu: the plan takes the workout as it stands, warmups aside, lands at the end of the rotation, the workout links to it, and the editor opens on it to be named and pruned.

## Screens

Every screen must justify its existence.

- **Train** — the loop above while a session runs; idle, the place one starts, by the plan the rotation names, by another, or empty. One tab, two screens, one address each; the live one goes by its plan's name, or Workout when it was started empty, and its bar counts the sets instead. Leads the bar.
- **Templates** — Plan's first half; the list; a template's editor is its one surface — planning, deleting and starting all live there, and the offer from its newest session waits at its head until answered; a template that still says nothing (no name, no exercises) is never saved.
- **History** — a child of Progress, and where a session goes to rest: reached through Progress's Training frequency card, through a door on the idle Train screen, and by finishing a workout. Workout list + detail; repeat-this-workout, which lives here alone — in the bar on a desk, in the ⋮ beside editing and the plan link on a phone; drift-vs-template on the detail, and the offer to carry it into the plan (Finish).
- **Exercises** — Plan's second half; catalog + customs; detail carries history, the record set — **Heaviest ever**, or **Most reps** where the belt has always been empty and the reps are what the ranking read — the est-1RM trend and the calculator under it. History marks two days rather than one — **PR** on the session holding the Heaviest ever set, **Top e1RM** on the session that estimates highest — and marks the set that earned each, because ten at ninety and three at a hundred are two achievements and a list that flagged only the heavier left the harder session unremarked. Usually they are the same row and it carries both badges; when they part, the second is the whole point. The estimate's badge was **Best** until the swap picker's raw best said Best too and one word meant two numbers; a tap on the History heading says which mark is which. In All each session names the grip it was done with, and its sets read as the ledger does — `10 reps`, `+5 × 8` — never `0 × 10`.
- **Body weight** — the Weight tab, the short word being the one a tab label holds; today's weigh-in first, then log + trend. Half of what v1 tracks, and touched every morning rather than on training days — the door that earns is the bar, not the foot of another screen. Progress keeps its Body weight card, now a summary pointing at the tab.
- **Progress** — five cards, one subject each, no configuration: **Weekly work** (tonnage and working sets, twelve weeks) · **Strength** (recent raw PRs, est-1RM direction on main lifts) · **Training frequency** (sessions in the last seven days vs your own median — facts, never streaks) · **Sets per muscle** (working sets by muscle, split direct/indirect) · **Body weight** (trend). A card earns its place by stating one thing about your own training you could not work out in your head, and by pointing at where that thing is logged; anything else stays off, with no exceptions. Headings state rather than ask — the card is the answer, so the heading naming it as a question made the card say everything twice. Every window rolls back from now and none is anchored to a weekday: "this week" meaning "since Monday" drew a Tuesday morning as a collapse. Weekly work takes the full width, being the one card that is mostly chart; the rest are two columns from `lg` and one below, capped rather than uncapped, so a desk window holds the screen at once and a phone gets two subjects before it scrolls rather than a single card of personal bests.
- **Settings** — a tab like any other. On a desk the bar reaches it from every screen, a live session included; on a phone the session keeps the bottom edge for itself, and back is the way out to the tabs.

The bar is **Train · Plan · Progress · Weight · Settings**. It read left to right as the tense of what each tab holds until Weight joined it — a daily act has no tense, and that reading was prose the bar got arranged for rather than anything the lifter was handed. Weight sits beside Progress, the two screens you open for a number rather than to lift. One bar serves both viewports: the tabs sit along the bottom on a phone and inside the top bar on a desk. No screen draws chrome of its own. On a phone the top bar holds back, a title and at most one act, and a tab root has none of them to give: the lit tab already names it, so the bar folds to the status-bar inset and the page starts under it, coming back only to hold the rest clock. Plan is the root with something to put there — its Templates · Exercises segment, which rides the bar so it stays put whichever half scrolls; Exercises' search scrolls with the list it filters. A screen whose own content says its name — the plan editor's name field — leaves the bar untitled until that field has scrolled away. Every control in the bar is drawn the same way, without a border: the bar's surface on the canvas is what sets them apart, and the bar itself has no rule under it for the same reason.

**Back is one act**, whichever back is pressed — the ‹ in the bar, the phone's own, the browser's — and it always lands in the same place. It closes what is open first: a sheet, a dialog, a tip, the record editor. Then it goes where the screen was opened from when the link said so, the exercise opened from the session walking back into the session rather than into the browse list it is filed under; up the hierarchy when nothing said; out of the live session to wherever the lifter came from. When that place is the entry behind, back pops it, and anywhere else it takes the current entry's place, so going back never grows the history a browser's own back would then replay. A tab is a peer and back leaves the app from one — except a tab glanced at from a running session, which walks back into it. A jump whose source is spent replaces rather than pushes, for the same reason: deleting a workout or a plan, finishing (the record takes the session's place), adding an exercise to the workout from its own screen. An address the app no longer answers at forwards to the one that replaced it, and one that never held anything still draws the bar and the tabs around saying so.

## Offline

- **On the device: everything** — templates, catalog + customs, full history, body weight.
- **The server is optional.** The phone is complete standalone: install, lift, export, forever. Connecting a self-hosted server adds sync, the web surface, and the API/MCP.
- **Sync** is opportunistic push/pull. Conflicts are last-write-wins per record; no merge UI. A finished, synced workout is never clobbered. It runs on launch, three seconds after a write, when the network returns, when the app comes back to the foreground, and on a tap; a server that does not answer is tried again on a short ladder rather than left until the next of those, which is what the launch used to be alone in doing.
- **Sync failing stays silent, sync being stuck does not.** A phone in a gym loses its network constantly and a message about each attempt would be noise, so a failed exchange still says nothing. What Settings does say is durable: how many changes are still only on this phone, when sync last reached the server, and — the distinction the row exists for — whether the wait heals itself or needs a person. Offline heals. No server named, a credential dropped under a 401, or a store belonging to another account do not, and until they were named a phone that had quietly stopped syncing looked exactly like one that had not.
- First install works immediately, empty and serverless. New device with a server: sign in → full pull → identical.

## Data-out

- **Export** is generated on-device, no server required, from the Data section in Settings. Two shapes: a lossless JSON dump (every live record of every kind as it is stored rather than as a screen reads it, the session in progress if there is one, and the format version, app version and moment it was made — sufficient to rebuild the database) and spreadsheet-shaped CSVs, two files and no zip (one row per set: date, plan, exercise, set number, type, weight, load mode, reps, RPE, grip, arms, whether it was done, the load with the body counted wherever the body is part of it, and the note the session left on the exercise; body weight as date, kg). A superset's rows run round by round, the order it was lifted in, and a warmup takes no set number, as on the record. On the phone both go out through the share sheet, because the WebView cannot download a file.
- **Import** reads that JSON back. It says what the file holds — workouts, plans, weigh-ins and settings counted, and the dates they span — and writes nothing until asked. It merges rather than replaces: every record goes through the rule sync already uses, so a copy on the phone that is as new or newer stays, nothing is deleted, and what comes in syncs like anything logged here. A session in progress comes back only to a phone that is not running one. A file from a newer format is refused in a sentence rather than half read, and a damaged one is refused whole.
- **API:** token-authenticated REST on the server — everything the app can do, readable and writable. Not built. `/api/sync` is the only way in and out today and it speaks records rather than the domain: opaque payloads under four kinds, last-write-wins, incurious about what any of them mean. The layer that would carry REST is the one MCP grew, `src/lib/server/mcp/library.ts`, and it is deliberately not MCP-shaped.
- **MCP:** the server speaks MCP at `/api/mcp` — Streamable HTTP, authenticated by an `api` token minted in Settings, where the address is named beside the token list because the secret is shown once and the host is needed every time; stateless, because nothing between two calls is worth remembering and the unit restarts on every deploy. The surface is chosen rather than mirrored: a tool answers a question the lifter would ask — what is this movement, what did I lift, how is it going, what trains next, log this morning's kg — rather than exposing a table, and the numbers it quotes come from the modules the phone computes with, so a personal best read here and read on the device are the same number rather than two that agree for now. It reads all of it: the catalogue and one exercise's whole history, sessions in list and set by set with their drift from the plan that started them, the plans in rotation order with the one that comes next, the five Progress cards in a single call, the weigh-in line with its rolling average. It reads it lean, because a caller pays for every row it is handed and reads far fewer than it is given: the catalogue comes back as identity — a name, its equipment, the muscle it is for — and history joins it only where a call asks for `detail`, an archived plan comes back as the name it lends old sessions and not the tree nothing can start, and a caller told the catalogue is closed in the same breath is a caller that substitutes rather than searching a third way for a movement that was never there. It writes what the app writes — a plan created, renamed, marked, archived or deleted; a logged session corrected, retimed or removed; a standing note, a rest duration, this morning's kg — and one thing the app cannot: a session that already happened, written straight into history, for the workout trained away from the phone. The rotation is the one thing it writes differently from everything else: a plan is a record and several can be saved at once, but the order they train in is one fact spread across all of them, and a caller moving plans through it one at a time aims each move at positions the move before it has already shifted — so the whole order is stated once, written in one transaction, and no version is quoted for it because nothing but the rank is that call's business. Other writes state the version they expect to overwrite and are refused when the record has moved since, which is the guarantee sync leaves to the client and cannot ask of a caller editing history it read a minute ago; a tree sent — a plan's exercises, a session's sets — replaces the whole of it, and what the schema does not model is carried over rather than restated, so a rename never moves what trains next. What MCP cannot see is a session in progress: a workout reaches the server when FINISH is tapped and not before, so it knows history exactly and is silent — honestly, and by saying so in its own instructions — about the bar you are standing at.

- **No v1 importer.** None ships and none is planned — but the operator's own v1 history was moved across once, on 2026-08-20, by a throwaway script pushing 153 records through `/api/sync`: 56 workouts and 91 weigh-ins from 2025-12-28 to 2026-08-01, plus v1's six plans imported archived so `workoutTitle` still resolves a name through `templateId` without the old plans crowding Plan or the idle Train screen. The two datasets are contiguous rather than overlapping — the switch happened on 2026-08-02 — so nothing merged and nothing was overwritten. One v1 session was dropped: a plan started that morning, never logged, and repeated in v2 fourteen minutes later. v1 exercises resolved to catalog slugs by hand; where a real movement had no entry, the catalog grew one (`decline-bench-press`, `incline-machine-chest-press`, `machine-curl`), and the rest folded into their nearest slug, which merges their history and PRs and is the one lossy thing here. v1 stays online at `v1.kilorep.com`, untouched, as the record of what was folded.
